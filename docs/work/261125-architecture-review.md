# Tend architecture review

Reviewed Tend at `c0e0be0`, including the proposal-status work two commits ahead of the local `origin/main`, and the adjacent Grove checkout at `3cfd2ef`. This is a review of the current system and of what will change as the same runner accumulates projects, attempts and approvals.

**Keep the division between Grove and Tend.** Grove can explain the scope someone approved at a Git commit. Tend can run agents, recover their turns and deliver a candidate. GitHub can enforce the final merge rules. The most consequential defects occur where one of these systems guesses what happened in another. Two already reproduce on a disposable Git repository, and two more reproduce through Tend’s acceptance harness. They deserve attention before increasing concurrency or giving the runner more authority.

## Two failures reproduced with Git and Grove

### 1. A claim can change the owner's staging area in another worktree

I left a tracked file edited on a checked-out `main`, added a different file upstream, and claimed a cycle from a clean linked worktree. The claim succeeded. Before the claim, the owner's status showed only their edit. Afterwards it also showed the upstream file as a **staged deletion**. A subsequent commit can silently undo someone else's addition. The original local edit survived this experiment.

Tend's synchronization code tries to leave a dirty target checkout alone. Grove subsequently advances the same local branch with `git update-ref`. The owner’s index and files still describe the earlier commit. Even a clean target checked out elsewhere is susceptible if it lags when Grove advances it. Have Grove resolve implementation scope from the commit in the claim, and let the attempt worktree point there. Reading scope at that commit also removes Tend’s reason to fast-forward a person's local target during routine scheduling. The regression check should compare the owner's branch, index and files before and after a claim from a sibling worktree. [Tend target sync](../../main.go#L299) · [Grove claim](https://github.com/mascah/grove/blob/3cfd2ef/internal/cli/claim.go#L139)

### 2. A failed setup can leave a successful shared claim

Grove writes the attempt to `grove/runs` before creating the attempt branch. In a disposable clone with a local branch named `grove`, branch creation failed because Git could not also create `grove/<id>`. The remote ledger already held the claim. A second ordinary claim said the work was in flight on a branch that had never existed. Killing the process between these two operations presents the same recovery problem. Tend treats a nonzero exit as a refusal and tries to discard the setup worktree. Watch only discovers interrupted attempts after local run metadata exists.

Keep Grove’s compare-and-swap on the ledger. Give the caller a stable claim identifier and a way to distinguish refusal, recorded claim awaiting local setup, and ready checkout. Make completing local setup for that identifier repeatable. Tend should write its setup intent before claiming, reconcile the ledger before cleanup, and preserve the checkout when ownership is uncertain. Test termination before and after the ledger update and before the first Tend status write. An automatic retry that simply takes another claim would forfeit the overlap guarantee. [Tend setup](../../attempt.go#L223) · [watch recovery](../../watch.go#L183) · [Grove commit order](https://github.com/mascah/grove/blob/3cfd2ef/internal/cli/claim.go#L127)

## Before broadening autonomous landing

### 3. A passing review can answer a different scope question from the owner's

Grove deliberately allows an implementer to revise a proposal on the implementation branch and records what merging it will approve. Tend tells the reviewer to find the requirements in the folders the candidate moved into the archive. Its completion check accepts the presence of a matching archive path. Grove itself permits archiving both finished and dropped changes. A competent reviewer can read the Git diff and catch a weakened requirement, but the review contract does not require a separate answer about what changed since approval. In a supervised PR the owner can make that judgment. In autonomous landing the scope revision and its implementation can acquire approval together.

Use the claim commit as the reviewer's independent reference. When scope changed, ask the reviewer whether the code satisfies the resulting scope, and whether the revision stays within the authority the owner delegated. Have Grove expose its existing scope comparison and finished/dropped distinction in a machine-readable form. Tend can then present or hold consequential revisions before landing. Preserve ordinary implementation choices and recorded incidental file changes. A good acceptance case is an implementation that passes every revised scenario after removing one approved behavior. [Tend's review inputs and completion check](../../attempt.go#L250) · [review prompt](../../flows/prompts/review.md) · [Grove revision rules](https://github.com/mascah/grove/blob/3cfd2ef/internal/instruct/requires/implement.md) · [Grove archive](https://github.com/mascah/grove/blob/3cfd2ef/internal/cli/archive.go#L20)

### 4. The evidence for independent review shares the implementer's write boundary

Both agent roles receive the run directory as a writable location. It holds the reviewer’s verdict as well as the controller’s prompt and recovery records. Recovery accepts an existing valid verdict for the head. The bot token is obtained through an account available to the runner's OS user. Separate conversations are valuable for independent judgment, but file shape and a matching SHA can only validate the contents of a report. They cannot establish which role produced it. This matters increasingly when the bot can merge protected work.

Give each role its own output location and give the controller exclusive write access to accepted verdicts and recovery records. Bind accepted results to the attempt, reviewer session, policy revision and head. Isolate publishing credentials from agent processes with an OS or credential boundary, and enforce required checks on GitHub with a publishing account subject to those rules. This costs more than changing the prompt. It is worth doing before treating the review status as independent authorization for an unattended merge. [Agent startup](../../flow_run.go#L172) · [result reuse](../../flow_run.go#L332) · [bot credentials](../../publication.go#L28) · [recognized ceiling](../../guide/built-vs-planned.md)

### 5. Protected-path approval uses an association that can exceed the person's authority

Tend accepts `OWNER`, `MEMBER` or `COLLABORATOR` on a GitHub review as evidence of write access. The code explicitly acknowledges that a read-only organization member counts. The same predicate drives change requests, approval detection and protected-path holds. An organization adopting a configuration that worked for a personal repository can grant more authority than its merge policy describes.

Resolve the reviewer's effective permission or use the repository's required-review decision for the relevant head and rule. A permission lookup failure should hold an authorization decision for retry. Keep the head check and validate the case of a read-only organization member alongside a writer, a dismissed approval and a later commit. [Authority predicate](../../publication.go#L406) · [protected-path decision](../../landing.go#L102)

### 6. Recovery replays old evidence under whatever flow the target serves today

Tend loads the current target’s flow on each invocation and walks it from its start. Prompt records are keyed by step name and often head. They contain no digest of the instruction or flow that produced the result. If the team strengthens a review prompt while a PR waits, rerunning can reuse the old verdict under the same name and SHA. Renaming a step can instead lose its history and consume another turn. A target ref can also move between loading the graph and reading a prompt.

Record an immutable execution definition per attempt, including the resolved target commit and the built-in flow/prompt version where used. Bind results to that definition. Keep current protected-path and merge rules live at landing. For an urgent policy change, explicitly invalidate the affected verdict and rerun the affected step. For existing attempts whose historical policy cannot be recovered, mark that fact and require a fresh review when current policy demands it. [Flow loading](../../flow_load.go) · [replay and record naming](../../flow_run.go#L41)

## Where to spend design effort

The current project already illustrates the limits of file-based planning. On this checkout, `grove check` reported that three files in the notification change (`261125-kvarn`) had moved since its proposal. Grove separately reported that its planned edit to `intake.go` overlapped an in-flight change. Both observations are accurate, and they call for different actions. One invites someone to reread a diff. The other reserves a file until the preceding work resolves. As more changes name the same orchestration files, the owner will see more revisions and less parallelism. Conversely, two changes to different files can alter the same behavioral contract. Track how long claims wait and how often combined CI or review finds an interaction before changing Grove’s overlap rule. In Tend, move logic behind a boundary when that makes a recurring change local. Extracting the permission decision used by watch, requests and landing is a concrete first example. [Grove overlap rule](https://github.com/mascah/grove/blob/3cfd2ef/internal/cli/claim.go#L254) · [pending notification change](../../grove/changes/261125-kvarn-say-what-the-owner-is-asked/tasks.md)

1. **Fix checkout ownership and partial claims first.** Both failures occurred without agents, GitHub, or unusual timing. Grove already records the target commit. Using it directly removes a shared mutable dependency. An idempotent handoff also gives operators a way to recover without guessing whether a retry is safe.
2. **Make an attempt a versioned, inspectable record in Tend.** Start with repository identity, work item, claim ID and base, execution definition, accepted results, and the reason it is waiting. Keep immutable evidence files and the current CLI. Put reading, transitioning and writing this record behind one Go type. Have watch and status read it through the same functions. Compatibility matters because the people most likely to upgrade have attempts in progress. A general-purpose workflow service would add migration cost without fixing the checkout or authority issues.
3. **Make the approval question explicit before adding autonomous proposal approval or a standing agent.** Separate the original agreement, revisions introduced while building, the evidence for the candidate head, and the actor authorized to accept a revision. Clean merges can also change runtime behavior when two separately correct changes interact. Keep exact-head CI, surface what verdict was carried, and require fresh review where the combined change affects a project-defined critical contract. [Clean-merge carry](../../landing.go#L40) · [autonomous direction](261121-autonomous-direction/direction.md)
4. **Make scheduling cost follow active work.** Keep the current polling approach, add terminal dispositions and pagination, then measure. An idle repository with a long history should produce roughly the same remote traffic as a new idle repository. Keep Git and Markdown as Grove's durable model. A narrow read path and reuse within one pass are compatible with Grove’s constitution, especially rules 2, 7 and 10. Any change to shared claim semantics should be reviewed against rules 2, 10 and 11. [Grove constitution](https://github.com/mascah/grove/blob/3cfd2ef/CONSTITUTION.md)

The existing acceptance suite is valuable because it drives the CLI against real Git and Grove. Extend it across interruptions at each durable boundary, flow upgrades with a pending review, multiple checkout paths, external-service read failures, and many retained completed attempts. The terminal and hosting stand-ins also leave a separate operational question about real dialogs, permission decisions and branch rules. Run a small provider contract check in a disposable integration repository when those contracts change. [Acceptance harness](../../scenario_test.go) · [terminal dialog handling](../../terminal.go#L48)


## Verification

Tend’s existing acceptance suite passed in 226 seconds. `go vet ./...` passed. Two additional temporary CLI scenarios used real Git and Grove with the repository’s provider and terminal stand-ins. Changing the review prompt on the target and resuming the same candidate produced a second success with no new reviewer turn (finding 6). Using a custom verdict filename produced local success and a PR, with zero review posts and zero writes of the required status (finding 10).

The checkout and partial-claim experiments used local bare remotes and the installed Grove build from `3cfd2ef`. The queue-cost projection is based on the call paths and one timed project read. Live GitHub rules, Jira, agent sessions, and sustained multi-runner load were outside the verification performed. The report is the only change to either project.
